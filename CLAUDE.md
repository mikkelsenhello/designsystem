# Designsystem

A rebrandable, reusable design system, consumed by separate projects (first the newsletter landing page on Vercel, later "Husk og gjør" and others) as a pinned git dependency — not copy-pasted.

## Standing instructions

- **Read `PLAN.md` first**, every session. It holds the full architecture, the phase breakdown, and decisions already made (stack, distribution, license, repo). Don't re-decide something `PLAN.md` already settled — check it before asking the user again.
- **Token-only styling, no exceptions.** No raw hex/rgb colors, no raw spacing/radius/shadow numbers, and no Tailwind arbitrary values (`p-[13px]`, `text-[#fff]`) anywhere outside `tokens/`. If a value is needed that no token covers, add a token (and say so) — never reach past the token layer. Component tokens (`tokens/components/*.css`, declared on `:root`) are for sizes, radii and borders only: a color token there that points at a context color (`--ds-color-base-default`) is resolved at `:root` and ignores the chip's/button's `data-color`. Context colors go through the Tailwind classes in `tokens/tailwind.css` (add a class there if one is missing).
- **Every component gets a colocated `README.md`** (`src/components/<Name>/README.md`): use for / **don't use for** / props / a wrong→right example. The "don't use for" line is mandatory, not optional — it's what stops a duplicate hand-built version of a component from appearing elsewhere in a consuming app.
- **Keep `docs/component-index.md` short** (under ~150 lines). It's the always-loaded index a consuming project's own CLAUDE.md points at before writing any UI — if it gets long, that's a sign to trim descriptions, not to let it grow.
- **Repo is public, all-rights-reserved** (no OSS license file). designsystemet.no's token *values* are MIT-licensed and attributed in `NOTICE.md` — that attribution stays regardless of this repo's own license.
- GitHub: `github.com/mikkelsenhello/designsystem`.
- **Consumers install a pinned tag** (`#v0.2.0`). Setup steps live in `README.md` → "Using it in a project"; update them whenever `package.json` exports, `tokens/index.css`/`base.css`/`tailwind.css`, or required peer setup change. Anything a consumer must import has to be listed in `package.json` `files`.
- **First consumer:** the "Hva skjer" website at `C:\Users\onkel\Documents\Prosjekter\Hva skjer\Nettside` (a growing multi-page site, worked on in its own Claude session). **The site builds first, the design system catches up** (decided 2026-10-17, see `PLAN.md`): Nettside never waits on this session. It builds what's missing itself, overrides design system components when they don't fit, and logs every such piece in its `docs/local-components.md` with status `candidate`. This session then decides what becomes standard:
  - **At session start, harvest.** Read Nettside's `docs/local-components.md` (rows with status `candidate`), grep its `src/` for `ds-allow: override` / `ds-allow: draft` lines that have no row yet, and check `docs/ds-requests.md` here for orders (create it if missing). Report the candidates to the user with a recommendation for each; don't start building before the user picks.
  - **Decide per candidate:** would a different app with a different brand use this as-is? **Yes →** promote: build it here as a proper component (or add the missing variant/token to the existing one, for an override), release it, then set the row to `promoted vX.Y.Z → replace`. **No** (brand values from outside the system, like the e-mail template; content-named; refuses theming) **→** set it to `local`; it stays in Nettside, owned by that session. **Override that fights the system** (e.g. restyles a color outside the context-color model) → `rejected: <why and what to use instead>`. In Nettside this session writes only the Status column of that table; the code there belongs to Nettside's session.
  - **Orders still exist** for when Nettside would rather have it done properly first: a cross-session message from the open `nettside-*` session, or an entry in `docs/ds-requests.md` (the only file in this repo Nettside writes). Same rules as promotions.
  - **Base it on designsystemet.** Every promotion or order is built as the matching designsystemet.no component (its anatomy, variants, naming, states, accessibility), implemented on our token layer per `PLAN.md` — not their code. If designsystemet has no such component, build it as an extension in the same token-driven way and say so. Don't invent a bespoke component when designsystemet already has one that fits.
  - **Work from their source, not from memory or the docs site.** Before writing anything, fetch the component's CSS and React source from `raw.githubusercontent.com/digdir/designsystemet/main/` (`packages/css/src/<name>.css`, `packages/react/src/components/<name>/`, plus `input.css`/`base.css` for anything they compose). Turn each of their `--dsc-<name>-*` variables into one of our tokens (same size step, radius, border, color role), and copy their states (hover only on hover-capable devices, checked, disabled, focus) and their markup (which native element, what stays visible, what screen readers hear). The first Chip skipped this and missed the height, the border, the visible input and the checkbox-vs-radio shape.
  - **Compare when done:** in the playground, measure the rendered component (height, padding, radius, border) against their numbers, not just by eye. List any of their variants you didn't build, and tell the user.
  - **Take the site's version as the brief, not the spec.** It shows what was needed (props, states, look); the promoted component follows designsystemet and our tokens, so its API may differ. Say how in the release note, so the replacement is easy.
  - **Build only what was ordered or picked**, under this repo's normal rules. Anything that would change a decision in `PLAN.md` goes to the user first.
  - **If an order conflicts** with the design system's principles (or with designsystemet's version of the component), reply with the concern and a proposed alternative instead of building it.
  - **When released:** tag a new version (`v0.2.0` …), mark the order done in `docs/ds-requests.md` if it came from there, set promoted rows in Nettside's `docs/local-components.md` to `promoted vX.Y.Z → replace`, tell the user the `npm install "github:mikkelsenhello/designsystem#<tag>"` line to run in that folder, and reply to the ordering session (copy the `from` of its message; for file orders, find the open `nettside-*` session with ListAgents) with the tag and a short usage note, e.g. "Released v0.3.0: Card (README at src/components/Card/README.md), replaces your local EventCard: `title` → `heading`". Nettside's session does the replacement (bump the pin, swap the import, delete the local copy/override and its row).
- **Before calling work done:** `npm run check` (token wiring + `check-ds` lint + types), and look at the change in the playground (`npm run playground`, light + dark side by side).
